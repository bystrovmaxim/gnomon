# Changelog

## [2026-11-11] — The plugin template keeps its history: any moment, editing, revisions and the time scale's data

The plugin template, which every Maxitor plugin is written from, now keeps its whole history. Its notes read at any past moment exactly as they were then, and the same question always gets the same answer; a moment that has not come yet is refused. A note is edited or deleted with the moment the person saw: if someone else changed or deleted it in between, nothing is overwritten and the answer says who and when. An item's notes can be published as numbered revisions — v1, v2 — each with a title, its own words and, if wanted, a release label; between two revisions the published notes do not change, and the draft shows what changed since the last one. History is only looked at: nothing restores or rewrites the past.

The template also answers the core's time scale, which comes next: how many notes were added, changed and removed in each stretch of time — counted by the page's own query, so the counts match what the page shows — and its revisions as milestones, each with a card the core draws. How any plugin does this is now part of `maxitor-plugin-sdk` and checked by `maxitor-plugin-check`: the plugin declares which comparisons its pages can draw and keeps the answers in its folder `history/`.

The documentation of plugins moved to one place, `docs/plugins/`: the plugin concept and versioned storage, which now shows every rule on the notes. ([#97](https://github.com/bystrovmaxim/gnomon/issues/97))

## [2026-11-10] — Plugins in an organization: the marketplace, installing, disabling and enabling

An organization's administrator now installs plugins. Settings sits at the foot of the organization's tree, and its first page is Plugins: what the organization runs and what the marketplace offers, with one search over both. A plugin's details show its passport, its wheel and the tables it will have. Installing checks first that the plugin fits this Maxitor and that everything it needs is already installed, and names what is missing. A plugin can be disabled — its sections leave the tree, its data stays — and enabled again, but never so that an enabled plugin is left without one it needs. An organization can also add a plugin of its own, from a release on GitHub or GitLab or by uploading the file itself; no other organization sees it. All of it works on a phone.

A plugin brings no SQL any more. It describes its tables in `schema.yaml`, and Maxitor builds them, each with its history, by the rules of versioned storage. Every version of a plugin gets a database schema and a database user of its own, built once for all of Maxitor: the next organization on the same version builds nothing. That user sees only its own schema; what a plugin needs of the core — the time of a change, membership, a member's name — it asks the core's functions. The plugin template now works this way.

The work that creates schemas and users is done by a separate process, `maxitor-plugin-installer`, the only one that knows the password allowing it. The web part of the core never sees it. The installer checks each new version — downloads it, compares its hash, reads its files without running them — and finishes each install; whatever stops it halfway, it finishes when it starts again. `./scripts/core-stand.sh up` now runs it too and fills the marketplace with the template, and `check-core.mjs` installs it in the browser. Removing a plugin from an organization is the next step, bystrovmaxim/gnomon#94. ([#82](https://github.com/bystrovmaxim/gnomon/issues/82))

## [2026-11-10] — Maxitor's own core: signing in, organizations and the plugins' compatibility rule

Maxitor has a core of its own. A person signs in, registers an organization and lands in its frame at `/w/<code>`. The core keeps its own PostgreSQL database, in two schemas owned by its own role: `platform` for accounts, their ways in and one-time codes, and `organization` for organizations, their users and boundaries. Every table keeps its history, except the password's hash, which never enters it.

People sign in by email and password, with the email confirmed by a code from a letter sent through Yandex Cloud Postbox, or with Yandex ID or Mail.ru ID from anywhere. Google, GitHub and Facebook work only outside Russia, as Russian law requires. The country comes from the request's IP, an unknown one counts as Russia, and the rule is checked both when signing in starts and when the provider sends the person back. A new person ticks the consent box before the account exists. The pages Privacy and Delete my data are open to everyone, and one cookie, HttpOnly, keeps the session; the page's scripts never see it. A wrong password and an unknown address get the same answer. Codes, letters and passwords have limits; resetting a password stops older sessions from renewing. An account registers up to ten organizations. A code typed for an organization's address is checked as it is typed, and two people asking for one address at once are decided by the database. Someone else's organization answers "No such organization", exactly like one that does not exist.

The screens are a Next.js application drawn from the mockup, on a desktop and on a phone. Every address of the backend is an AOA action, and mail, the country of an IP and each provider are typed gateways. Every domain of Maxitor now writes only typed events. `./scripts/core-stand.sh up` runs the whole core on one machine, and `check-core.mjs` walks its scenarios in a browser — [Run Maxitor core locally](how-to/run-the-core-locally.md).

The core names itself in a passport: its version, the formats of a plugin's files it reads, and the SDK it is built with. A new package, `maxitor-plugin-sdk`, holds the schemas and checks of a plugin, moved from the plugin template, and the one decision whether plugins fit a core and each other; every refusal names every side. `maxitor plugin check <path> --core <version>` puts the two together and also refuses a plugin whose domain declares no events. The plugin template fits Maxitor 4.

The ERD's physical view paints by domains again when the reader chooses Domains. The concept model of spec 059 runs on the current AOA and names boundaries where it named enterprises. ([#73](https://github.com/bystrovmaxim/gnomon/issues/73))

## [2026-11-09] — The ERD's small fixes, found on the demo's history

Switching **Boundary** off no longer folds anything: the domains folded in the address used to vanish into bare ids with every line running to them, and the other tables stood in one tall column. Switching it off or on now replaces the drawing in one step, fitted to what it shows, with no frame between and no jump. The card of a frame keeps the pointed table's type and description in view at its bottom while its list scrolls, and the list no longer shakes under the pointer. Moving from a table onto its card keeps the table lit. A step through the changes lands on a change inside a folded frame too: its box lights and its card opens. A marked row's type no longer slides over its name when the drawing is zoomed in. The logical and the physical view each keep their own layout and tables' collapse, and a room carries both, and the halves of the events explorer. ([#89](https://github.com/bystrovmaxim/gnomon/issues/89))

## [2026-11-09] — The ERD of a large model stays live

On a model of a thousand tables the whole system's ERD used to stop the page: Graphviz laid the model out on the page itself for some twenty seconds, and every repaint and every unfold did it again. Now the first picture comes in under three seconds, and the page answers while a model is laid out: Graphviz and the drawing of the cards run in a Web Worker, beside the page.

The picture is made with stand-ins for the paint's colours, so one layout serves every paint. A repaint lays nothing out — the drawing on the page takes its new colours where it is, in about 70 ms. A fold or a filter change shows at once: what leaves the drawing leaves the current picture, and the new layout replaces it within a second. A room follower sees a received setting the same way. Zooming no longer stalls the page for seconds, and the server reads the tables of every domain in a few queries for the whole request, in half a second instead of two.

Nothing the reader sees changed. `client/scripts/measure-erd.ts` measures it, `--headless` without a window, and `specs/071-erd-frames-folding/measurements.md` keeps the numbers before and after. Three targets are still missed — placing a whole new picture blocks the page for about 0.6 s, a hover's highlight takes about 125 ms, and the one zoom frame that crosses from near to far about 170 ms — and are bystrovmaxim/gnomon#87. ([#85](https://github.com/bystrovmaxim/gnomon/issues/85))

## [2026-11-09] — The ERD's frames, folding and filters, the same in every layout

The ERD frames what it shows in both of its views and in all five layouts. In the logical view each domain is a frame, and **Boundary** in the toolbar switches the frames off and on; in the physical view each database is one frame holding its tables directly. Dot draws a frame as a cluster; Neato, FDP and Circo cannot frame the same way twice, so Maxitor composes their frames — each frame's tables laid out alone, a specialization block as one unit holding only its own tables, then the frames — and the same model gives the same picture on every load and in every browser. A frame's title is its disk and its name set as one label, the disk on the axis of the name's capitals, the title centred. Under Dot the parts of a model that no line joins are wrapped into columns, so a model of many unlinked tables or domains is drawn about as wide as tall instead of one tall thread.

A click on a frame's empty space folds it into one box with its disk, its name and what it holds; a click on the box unfolds it; the corner buttons are gone. The button beside Boundary folds or unfolds every frame at once, and the drawing fits again. Resting anywhere inside a frame opens its card, which now reads the domain's or the resource's description; pointing at one of its tables shows that table's description. A line's card is built as a table's is: the relation named by its field, `Association · many to one`, its description, and its two ends, From and To, each with the mark the line draws there and how many in words. A card stands beside what it describes and never over it. From afar, when a table's rows are too small to aim at, a hover anywhere on it lights all its lines; the rows' text is drawn as bars of its length and colour, so the picture looks the same and panning repaints far less.

Every diagram with a filter panel follows one rule. The scope is what the diagram is drawn for; on a domain's ERD and use cases, 1-hop adds what lies one relation away — for use cases, the use cases of other domains one include, extend, depends or generalization away, now that the page reads every domain's use cases — and the panel lists that base whether 1-hop is on or off. Switching a row off hides its elements even where 1-hop would bring them in; a row whose elements are all hidden stays, dimmed. The whole system's diagrams and a lifecycle are their own base and show no 1-hop switch. On the use cases of all domains each domain is a boundary in its colour, and folding the boundaries keeps every role linked, its generalizations too; with Boundary off nothing is folded. The fold of the use cases, and a lifecycle's filters and paint, now travel in the address and are shared by a room, and two tests check that the address and the room know every setting a page keeps.

The ERD of a large model is measured — `client/scripts/measure-erd.ts`, on models of 1 000 and 5 000 tables made by `generate-large-graph.ts --tables`: a fold and a filter change already answer within a second, while the first picture of 1 000 tables takes about 23 s of Dot's layout and a model of 5 000 tables does not draw at all; making both fast is bystrovmaxim/gnomon#85.

The demo's graph, `external/aoa` at the merge of bystrovmaxim/aoa#496, links seventeen pairs of entities across fourteen domains again, so neighbours, bundles between folded domains and filters can be tried on it. ([#80](https://github.com/bystrovmaxim/gnomon/issues/80))

## [2026-11-09] — How a Maxitor plugin is made, shown by one that is

Maxitor is going to host plugins: independent applications that install into it, keep their data in its database and show their pages inside its screen. Before the first of them is written, the rules they follow are written down and shown working in a new package, `packages/maxitor-plugin-template` — a small plugin, `notes`, that keeps notes on catalog items and has every part a real plugin has.

Its documentation lies beside it. [plugins.md](../packages/maxitor-plugin-template/docs/plugins.md) is the plugin concept: the passport a plugin declares itself by; how it depends on the core and on other plugins by version ranges, as pip requirements do, with the core as one more node of that graph and one function deciding compatibility everywhere; its own schema and database role, writing only its own tables and reading all others; foreign keys across plugins, declared by names alone and built by the installer, so nothing in the file can become SQL; one sign-in through the core's gateway, with a short token signed by the core for each plugin; the screen the core draws and the plugin only fills — the left tree it adds its nodes to, the right panel, one canvas, the controls over it — and an address that holds everything a person sees, the organization first, so Back, a link and a room work for every plugin alike. [versioned-storage.md](../packages/maxitor-plugin-template/docs/versioned-storage.md) says how tables, versions and time are kept so that any past moment reads by the same actions as the present.

The plugin itself follows them: its passport, its tree nodes and controls, its declared foreign keys and its first migration pass the checks the installer will make, kept in the package until `maxitor-plugin-sdk` takes them; its backend writes a note and its version in one transaction under the organization's lock, reads only version tables at one moment, accepts only the core's token issued for it, and touches an organization's data only for a member of it; its Next.js pages keep every view setting in their address. It does not run against Maxitor yet — the core that hosts it is the work of bystrovmaxim/gnomon#72 — and until then it runs in its tests.

## [2026-11-05] — The published wheel is checked before it goes out

Every pull request now builds the `maxitor` wheel and installs it into a clean environment, the way a user gets it from PyPI. It must ship only Maxitor's own code, install the `graph-builder` command without bringing AOA or any of the web part's libraries, and answer `maxitor` and `repo-graph-port` with the extra to install when that extra is missing. These checks lived in AOA's repository before the move and now run here, where the wheel is built and published.

## [2026-11-05] — Maxitor and the Open Gnomon Protocol have a home of their own

Maxitor used to live inside the AOA repository, next to the framework, and every change to AOA paid for Maxitor's checks — a pull request with no line of code still waited for its client to be drawn in three browsers. The two are different things: AOA is a Python framework, one of the programs that write a system's graph, while the Open Gnomon Protocol is the graph's language, which any program can write, and Maxitor reads any graph written in it.

This repository is now their home. Their whole history came with them, so `git log` and `git blame` on any file go back to its first commit, through every rename; issue numbers in old commit messages point to AOA's issues, where that work was done. The specs of Maxitor's work, its how-to guides and the Russian drafts beside them came too.

AOA is taken as a git submodule at `external/aoa`, fixed to one commit: Maxitor builds with exactly that AOA, and a newer one arrives only when `./update-aoa.sh` moves it, in a commit of its own. Clone with `git clone --recurse-submodules`.

For someone who uses Maxitor, nothing changes but the addresses. `pip install maxitor` installs the same package with the same commands. A project that checks its graphs in CI writes `uses: bystrovmaxim/gnomon/packages/maxitor/tools/graph-builder@maxitor-v<version>` instead of the old path under `bystrovmaxim/aoa`. Releases are published from here to PyPI by a trusted publisher, so no token is kept in the repository.

Each pull request here runs the same check run as before — the static checks, the tests of every part, the client's build and tests, the graph files and the versions — and the browser checks run locally with `bash scripts/check_before_pr.sh`, which leaves the status the merge rule of `main` requires.
